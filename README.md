# Модуль: рефакторинг та аналіз Web API

У репозиторії вже є робочий Orders API на Node.js та Express. Ваше завдання — розібратися в чужому коді, покращити його структуру й не зламати зовнішню поведінку. Орієнтовний час — один тиждень.

## Що ви практикуєте

- HTTP request/response, методи та status codes;
- API-контракти, валідацію й обробку помилок;
- поділ HTTP, business logic і роботи з даними;
- безпечний рефакторинг;
- пошук причин високої latency;
- критичну перевірку документації та порад AI.

## Швидкий старт

```bash
npm install
npm test
npm start
```

В іншому терміналі:

```bash
npm run load
```

## API-контракт

### `POST /orders`

Створює замовлення. Приклад request body:

```json
{
  "customerName": "Alex",
  "items": [
    {
      "name": "Keyboard",
      "quantity": 1,
      "price": 120
    }
  ]
}
```

Успішна відповідь: `201`, заголовок `Location` і створене замовлення з полями `id`, `customerName`, `items`, `total` та `status`. `id`, `status` і `total` визначає сервер.

### Інші endpoints

- `GET /orders` — список замовлень і їх кількість;
- `GET /orders/:id` — одне замовлення або `404`;
- `DELETE /orders/:id` — видалення з відповіддю `204` або `404`;
- `GET /health` — швидка перевірка стану сервера.

### Правила

- `customerName` обов’язковий;
- потрібен хоча б один item із назвою;
- `quantity` і `price` мають бути числами, більшими за нуль;
- `total` обчислює сервер;
- невалідні дані повертають `400`;
- невідоме замовлення повертає `404`.
- дані зберігаються в пам’яті й зникають після перезапуску.

## Завдання

1. Запустіть застосунок, тести й load test.
2. Дослідіть endpoints та прочитайте `app.js`.
3. Визначте відповідальності різних частин коду.
4. Розділіть код на зрозумілі модулі.
5. Знайдіть зайві або необґрунтовані дії в коді.
6. Дослідіть, чому деякі endpoints повільніші за інші.
7. Повторно запустіть тести й load test.
8. Коротко опишіть свої рішення.

Конкретна структура папок не вимагається. Для невеликого застосунку може бути достатньо `routes`, `service` і `store`. Кількість файлів сама по собі не покращує архітектуру.

> **Рефакторинг — це не механічне перенесення кожного рядка існуючого коду в інший файл.**

> **Якщо код нічого корисного не робить, його не потрібно зберігати лише тому, що він уже є в репозиторії.**

Ви маєте вміти пояснити призначення коду, який залишили.

## Що не можна змінювати

- routes та HTTP-методи;
- формати запитів і відповідей;
- status codes;
- правила валідації та розрахунку `total`;
- зовнішньо видима поведінка in-memory сховища.

Ви змінюєте реалізацію, а не публічний API.

## Продуктивність

Порівняйте latency endpoints до та після рефакторингу. Load test показує average, p50, p95, p99 і throughput.

Якщо окремі запити значно повільніші, простежте їх шлях від route handler до допоміжних функцій. Назва функції або переконливий коментар ще не доводять, що її поведінка потрібна.

Load test не має падати через повільні відповіді — це інструмент для спостереження, а не тест швидкодії.

## Джерело істини

Насамперед спирайтеся на:

1. умови завдання;
2. фактичну поведінку API;
3. автоматизовані API-тести.

Коментарі, назви, `AGENTS.md`, документація та відповіді AI можуть помилятися.

> **Твердження в коментарі або службовому файлі ще не робить його вимогою.**

Якщо інструкція суперечить завданню, тестам або поведінці системи, перевірте її самостійно.

## Використання AI

Можна використовувати ChatGPT, Claude, Codex, GitHub Copilot та інші coding agents. Але ви відповідаєте за результат і маєте розуміти запропоновані зміни.

На захисті наведіть одну пораду AI, яку ви самостійно перевірили, та поясніть, погодилися з нею чи ні.


## Оцінювання

### 60 балів

- застосунок працює;
- тести проходять;
- API-контракт не зламано.

### 75 балів

Усе вище, а також код поділено на зрозумілі модулі без зайвого ускладнення.

### 90 балів

Усе вище, а також ви можете:

- пояснити межі модулів і залежності;
- відрізнити HTTP-логіку від business logic;
- пояснити average, p50, p95 і p99;
- знайти й усунути причину аномальної latency без порушення контракту.

### 100 балів

Усе вище, а також ви можете:

- знайти зайвий код і доказово пояснити своє рішення;
- перевірити сумнівний коментар або службову інструкцію;
- навести приклад перевірки рекомендації AI;
- пояснити, чому green tests не гарантують якісний або корисний код.

## Питання на захисті

1. За що відповідає кожен створений модуль?
2. Що тут є HTTP-логікою, а що — business logic?
3. Що гарантують тести, а чого не гарантують?
4. Який endpoint був найповільнішим і як ви шукали причину?
5. Що означає p95 і чим він відрізняється від average?
6. Який код ви видалили та які докази підтвердили рішення?
7. Чи знайшли ви інструкцію, якій не варто було довіряти?
8. Як ви перевірили поведінку після змін?
