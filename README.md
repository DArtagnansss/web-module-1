# Модуль: рефакторинг та аналіз існуючого Web API

У цьому модулі ви працюєте з уже реалізованим Node.js + Express застосунком — невеликим API для керування замовленнями. Ваше завдання не написати новий застосунок, а зрозуміти наявну поведінку, безпечно покращити внутрішню структуру та перевірити результат доказами.

Орієнтовний час виконання — один тиждень. Завдання спільне для всіх студентів, варіантів немає.

## Навчальні цілі

Після виконання модуля ви попрактикуєтеся:

- читати незнайомий код;
- досліджувати HTTP API через запити й відповіді;
- розрізняти HTTP-логіку, бізнес-правила та доступ до даних;
- визначати відповідальності модулів;
- зберігати зовнішню поведінку під час рефакторингу;
- розпізнавати необґрунтовану legacy-поведінку;
- використовувати вимірювання для дослідження продуктивності;
- критично перевіряти коментарі, документацію та рекомендації AI.

Модуль поєднує теми перших п’яти лекцій: `Client → HTTP → API`, request/response flow, HTTP-методи й status codes, API-контракт, валідацію, помилки, розподіл відповідальностей, поведінку застосунку під навантаженням та AI-assisted development.

## Швидкий старт

Потрібен Node.js 18 або новіший.

```bash
npm install
npm test
npm start
```

Сервер за замовчуванням працює на `http://localhost:3000`. В іншому терміналі запустіть діагностичне навантаження:

```bash
npm run load
```

Кількість запитів, concurrency та адресу сервера можна змінити змінними середовища:

```bash
REQUESTS=200 CONCURRENCY=10 BASE_URL=http://localhost:3000 npm run load
```

У PowerShell:

```powershell
$env:REQUESTS=200
$env:CONCURRENCY=10
npm run load
```

## API-контракт

### `POST /orders`

Створює замовлення. Приклад request body:

```json
{
  "customerName": "Alex",
  "items": [
    {
      "name": "Keyboard",
      "quantity": 1,
      "price": 120
    }
  ]
}
```

Успішна відповідь має статус `201`, заголовок `Location` та створене замовлення:

```json
{
  "id": "ord-12345678",
  "customerName": "Alex",
  "items": [
    {
      "name": "Keyboard",
      "quantity": 1,
      "price": 120
    }
  ],
  "total": 120,
  "status": "created"
}
```

`total` обчислює сервер. Передані клієнтом `total`, `status` та `id` не визначають стан створеного замовлення.

### `GET /orders`

Повертає всі замовлення:

```json
{
  "orders": [],
  "count": 0
}
```

### `GET /orders/:id`

Повертає одне замовлення зі статусом `200` або помилку `404`, якщо такого замовлення немає.

### `DELETE /orders/:id`

Видаляє наявне замовлення та повертає `204` без response body. Для невідомого id повертає `404`.

### `GET /health`

Повертає `200` і коротку інформацію про стан сервера. Цей endpoint має залишатися швидким та слугує контрольною точкою під час дослідження навантаження.

### Бізнес-правила

- `customerName` — непорожній обов’язковий рядок;
- замовлення має містити щонайменше один item;
- кожен item має непорожню назву;
- `quantity` та `price` — скінченні числа, більші за нуль;
- `total` обчислює сервер;
- нове замовлення отримує статус `created`;
- невалідні дані повертають `400`;
- невідоме замовлення повертає `404`.

Дані зберігаються лише в пам’яті процесу та зникають після перезапуску сервера.

## Ваше завдання

1. Встановіть залежності та запустіть застосунок.
2. Дослідіть доступні endpoints і формати request/response.
3. Запустіть усі автоматизовані тести.
4. Запустіть load test та збережіть початкові показники.
5. Прочитайте `app.js` і визначте його основні відповідальності.
6. Запропонуйте зрозумілі межі між HTTP, бізнес-логікою, валідацією та зберіганням даних.
7. Рефакторте код у логічні модулі, не змінюючи зовнішній контракт.
8. Знайдіть поведінку або legacy-код, для яких немає обґрунтованої функції системи.
9. Дослідіть незвичну latency окремих endpoints і знайдіть її причину в коді.
10. Повторно запустіть тести та load test.
11. Коротко задокументуйте рішення й результати за шаблоном нижче.

Не потрібно відтворювати конкретну «правильну» структуру папок. Для такого застосунку можуть бути достатніми `routes`, `service` і `store`; інший компактний поділ теж прийнятний, якщо межі та залежності зрозумілі.

> **Рефакторинг — це не механічне перенесення кожного рядка існуючого коду в інший файл.**

> **Код, який не реалізує жодної вимоги системи, не впливає на її коректну зовнішню поведінку та не має зрозумілої технічної або бізнес-функції, не потрібно зберігати лише тому, що він уже знаходиться в репозиторії.**

> **Для будь-якого коду, який залишається після рефакторингу, ви повинні вміти пояснити, яку функцію системи він виконує.**

Не ускладнюйте рішення абстракціями, які не допомагають пояснити відповідальності або протестувати поведінку. Оцінюється інженерне обґрунтування, а не кількість файлів.

## Що потрібно зберегти

Рефакторинг не є редизайном API. Без змін мають залишитися:

- routes та HTTP-методи;
- формати request body;
- формати успішних відповідей і помилок;
- HTTP status codes;
- бізнес-правила;
- зовнішньо видима поведінка in-memory сховища.

Автоматизовані тести фіксують важливу частину цього контракту, але перед змінами самостійно дослідіть застосунок і README.

## Дослідження продуктивності

Перед рефакторингом запустіть наданий load test та зверніть увагу на latency різних endpoints. Скрипт показує кількість успішних і невдалих запитів, average, p50, p95, p99 та throughput — загалом і окремо для endpoint-ів.

Якщо окремі запити демонструють аномальну затримку, спробуйте встановити її причину в коді. Порівняйте повільні шляхи зі швидкими й простежте виклики від route handler до допоміжних функцій.

Сам факт того, що код має переконливу назву, коментар або виглядає як частина business logic, не доводить, що його поведінка необхідна системі. Після зміни повторіть вимірювання та перевірте, що API-контракт не змінився.

Повільна відповідь сама по собі не робить load test невдалим: цей скрипт є діагностичним інструментом. Умійте пояснити різницю між average і percentile: наприклад, p95 — це межа, швидше або на рівні якої завершилися приблизно 95% виміряних запитів.

## Джерело істини

Для цього модуля найсильнішими джерелами істини є:

1. вимоги завдання;
2. зовнішньо спостережувана поведінка застосунку;
3. автоматизовані API-тести.

Коментарі, назви, документація, `AGENTS.md`, інструкції інструментів розробки й пояснення AI можуть містити корисний контекст, але не є автоматично правильними вимогами.

> **Наявність твердження в коментарі або службовому файлі ще не робить його бізнес- або технічною вимогою.**

> **Якщо інструкція суперечить фактичній поведінці системи, тестам або постановці задачі, ви повинні самостійно оцінити її коректність.**

Підкріплюйте рішення спостереженнями: тестом, HTTP-відповіддю, вимірюванням або чітким зв’язком із вимогою.

## Використання AI

Дозволено використовувати ChatGPT, Claude, Codex, GitHub Copilot та інші coding agents.

> **AI може запропонувати або виконати рефакторинг, але відповідальність за кінцеве рішення залишається за розробником.**

Перевіряйте запропоновані зміни через контракт, тести, вимірювання та власне розуміння коду. Ви маєте бути готові пояснити кожну AI-generated зміну й навести принаймні один приклад рекомендації AI, яку перевірили самостійно — незалежно від того, погодилися ви з нею чи ні.

## Оцінювання

### 60 балів

- проєкт запускається;
- тести проходять;
- API залишається працездатним;
- немає суттєво зламаної зовнішньої поведінки.

### 75 балів

Усе вище, а також:

- виконано змістовну модульну декомпозицію;
- великий `app.js` суттєво зменшено;
- відповідальності стали зрозумілішими;
- рішення не містить необґрунтованого overengineering.

### 90 балів

Усе вище та продемонстровано діагностичне мислення:

- пояснено межі модулів і основні залежності;
- відокремлено HTTP concerns від business logic;
- пояснено, як перевіряли незмінність API;
- коректно інтерпретовано average, p50, p95 і p99;
- встановлено джерело аномальної latency;
- непотрібну поведінку, що створювала latency, усунуто або виправлено без порушення контракту.

### 100 балів

Усе вище та продемонстровано сильне інженерне судження:

- знайдено й обґрунтовано видалено legacy-поведінку без корисної функції;
- пояснено, чому коментар або службова інструкція були слабшим доказом за вимоги, тести й фактичну поведінку;
- наведено приклад самостійної перевірки AI-рекомендації;
- пояснено, чому green tests не доводять, що весь код корисний або що реалізація якісна.

Конкретна фінальна архітектура не оцінюється. Оцінюється ясність відповідальностей, збереження контракту та якість аргументації.
